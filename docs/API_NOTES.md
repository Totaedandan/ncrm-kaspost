# Заметки по внешним API

Изучено 2026-11-02. Источники — в конце каждого раздела.

## Казпочта — трекинг (реализовано в `KazpostAdapter`)

Официальная документация: портал «QazPost Open API» https://open.post.kz, метод «Сервис трекинга по трек-номеру»
(данные портала отдаются JSON-ом: `https://open.post.kz/openapi/api/methods/15/details`).

- **Прод:** `GET https://track.kazpost.kz/api/v2/{ШПИ}/events` (также `track.post.kz`). Dev: `https://pls-dev.post.kz/api/v2/{ШПИ}/events`.
  Без авторизации. Старый адрес из SPEC (`post.kz/external-api/tracking/api/v2`) отвечает, но не является официальным.
- **Формат:** события сгруппированы по дням, внутри дня — от новых к старым:
  `{trackid, timestamp, events:[{date:"DD.MM.YYYY", activity:[{time:"HH:mm:ss", zip, city, cityKz, name, x_dep_id, status:["КОД"], dep_code, nondlv_reason, return_reason, forward_reason}]}]}`.
  Статус — **массив кодов** (`ISSPAY`, `STR`, `RCPOPS`…), а не текст.
- **«Нет информации»:** HTTP 200 и `{trackid, timestamp, exectime, error:"Отсутствует информация по данному трек номеру …"}`. На невалидный трек отвечает так же.
- **Справочник статусов:** https://post.kz/static/new_mappings.json (198 кодов, флаг `show`: 0 = внутренний, не показывать клиенту).
  Копия — `tests/fixtures/kazpost/new_mappings.json`; из неё генерируется `kazpost-status-codes.ts`
  (`node scripts/generate-kazpost-codes.mjs`). Классификация код → `TrackingStatus` — в этом скрипте.
- **Коды `*_UNDO[_I|_O]`** отменяют ранее вставленное событие (например `ISSPAY_UNDO` — отмена вручения); адаптер удаляет отменяемое событие.
- **Расхождение со справочником:** в реальном ответе встретились коды `New_act_B`, `Send_act`, которых нет в справочнике. Они добавлены в скрипт как внутренние (`OBSERVED_INTERNAL`). Новые такие находки приходят `DEV_ALERT`-ом «неизвестный статус».
- **Время** в ответе — местное, без пояса; считаем UTC+5 (единый пояс РК с 2024-03-01; для более старых данных будет сдвиг на час).
- Отдельный метод для грузовых отправлений: `https://pls.post.kz/api/v4/{ШПИ}/events` (другой формат, справочник `Statuses_API_v4.pdf`). Не используется.
- Реальная фикстура: `tests/fixtures/kazpost/real-delivered.json` (пример из документации, трек `AV005201643KZ`). Остальные фикстуры помечены `_synthetic` — построены в реальном формате.

Не выяснено: лимиты запросов, SLA, точная семантика `DLV_HAND` и `EDG` (считаем «в пути»), поведение после `*_UNDO` для уже терминального `DELIVERED` (не пересматривается).

## NCRM (реализовано в `NcrmAdapter`, проверено только на синтетических ответах)

Источник: https://helpdesk.ncrm.pro/article/api-dlya-razrabotchikov-ncrm/ (обновлена 15.09.2026) и приложенный к ней скрипт
`https://helpdesk.ncrm.pro/media/articles/files/2026/09/ncrm_api_2.py`. Статья «Начало работы с API» — пустая заглушка.

- **Нет сущности «заказ».** Есть клиенты (`contacts`), сделки (`deals`), воронки/этапы, задачи, пользовательские поля. Заказ = сделка (предположение), статус = `stage_id`.
- **Авторизация:** персональный токен в query `?api_token=…` (Профиль → «Ваш API token»). Для POST/PUT скрипт требует заголовок `referer: https://<host>/`. Срок жизни токена не указан.
- **Хост:** статья — `https://PODDOMEN.ncrm.kz/api/ENTITY/`, скрипт — `cloud.ncrm.pro`. Какой верный для клиента — выяснить.
- **Сделки:** `GET /api/deals/` (поля `id, created, changed, full_name, budget, responsible_id, stage_id, field_values, contact, phones, emails`),
  `GET /api/deals/{id}/`, `POST/PUT /api/deals/`.
- **Смена этапа:** `PATCH /api/deals/change_stage/` с телом `{"stage_id": …, "ids": [deal ids]}` → 204. В документации поле названо `Ids`, но NCRM отвечает 400 `{"ids":["Обязательное поле."]}` — рабочее имя `ids` (маленькими).
- **Этапы:** `GET /api/deals/funnels/` → воронки с `stages[{id, stage_name, funnel_id, sort_order, stage_group}]`.
- **Пользовательские поля:** `GET /api/custom_fields/` (`id, field_name, field_type, entity, options`); значения в сделке — `field_values`, при записи `[{"field": <id>, "value": …}]`.
  Трек-код и «способ доставки» — это, скорее всего, пользовательские поля сделки; их ID нужно найти в аккаунте клиента.
- **Комментарии:** только в скрипте, для клиентов: `POST /api/notes/contacts/{id}/` (multipart, поле `text` = JSON-строка `{"message": "…"}`). Для сделок (`/api/notes/deals/{id}/`) не подтверждено.
- **Документация НЕ описывает:** пагинацию, фильтры по `changed`/`stage_id` в списке сделок, формат ошибок, лимиты, вебхуки, песочницу, срок жизни токена, структуру `field_values` в ответе.
  Расхождения статьи и скрипта: `entity` (1/2 против "Deal"/"Contact"), `contact` как объект или массив, пользователи (`/api/crms/crm_users/` против `/api/groups/short/`).

Вопросы клиенту/поддержке NCRM — в SPEC §14; к ним добавить: правильный домен, пагинация и фильтр по дате изменения у `GET /api/deals/`, комментарии к сделкам, тестовый аккаунт.

### Рабочий процесс клиента (уточнено 2026-11-03, аккаунт `cloud.ncrm.pro`)

- Домен аккаунта — **`cloud.ncrm.pro`** (воронка «Воронка продаж», ссылка сделки `/deals/info/{id}`).
- Работаем только с колонкой **«НА ДОСТАВКЕ»** (сейчас ~184 сделки). Остальные колонки (ЗАКАЗ, ЗАКАЗ НА ПОДТВЕРЖДЕНИЕ, ОТКАЗ…) игнорируются.
- **Трек-код лежит в комментарии сделки** (отдельный комментарий, тело — только трек, например `UQ058702081KZ`), а не в пользовательском поле. Менеджер добавляет его при переводе сделки в «НА ДОСТАВКЕ». Поле «Доставка = Почта» есть, но не обязательно для фильтрации.
- Сценарий: трек из комментария → Казпочта → при статусе «Успешно вручено адресату» (`DELIVERED`) сделка переносится из «НА ДОСТАВКЕ» в **«УСПЕШНО ДОСТАВЛЕН»**. **Возврат** (клиент не забрал, посылка пошла обратно отправителю) → сделка переносится в **«КЛИЕНТ НЕ ЗАБРАЛ ОТКАЗ»** (`RETURNED`). Остальные статусы в CRM не пишутся (`CRM_STATUS_MAP` содержит только `DELIVERED` и `RETURNED`).
- **Возвраты:** признак — любое событие возврата Казпочты (`RETSTR`, `RET`, `RETSC` и т. п.; в ответе API также `isHasReturn: true`, `returnDate`). Как только оно есть, посылка `RETURNED` (терминальный статус), и последующее «Успешно вручено адресату» в пункте отправителя **не** считается доставкой: это отправитель забрал свою посылку (случай `UQ051789605KZ`: возврат 19.10, «вручено» 03.11 в Алматы). Отмена возврата (`RETSTR_UNDO`) снимает признак.
- Защита: перенос выполняется только если сделка всё ещё в «НА ДОСТАВКЕ» (читается `GET /api/deals/{id}/`). Если менеджер уже перенёс её (например, в «КЛИЕНТ НЕ ЗАБРАЛ ОТКАЗ»), обновление пропускается и логируется.
- Настройка: `NCRM_TRACK_SOURCE=comments` (по умолчанию), `NCRM_SOURCE_STAGE_ID` = id «НА ДОСТАВКЕ», `CRM_STATUS_MAP={"DELIVERED":"<id УСПЕШНО ДОСТАВЛЕН>","RETURNED":"<id КЛИЕНТ НЕ ЗАБРАЛ ОТКАЗ>"}` (сейчас 14276 и 18747). Id этапов — `pnpm ncrm:inspect`.
- Комментарии читаются `GET /api/notes/deals/{id}/` — **не подтверждено документацией** (там только запись для клиентов). Формат ответа тоже неизвестен, поэтому ищем трек во всех строках комментария; новейший определяется по дате (`created`/`created_at`/`date`), без даты — последний в ответе.
- Добавление комментария не меняет `changed` сделки (предположение) → при чтении треков из комментариев курсор игнорируется и каждые 10 минут перечитываются комментарии всех сделок этапа (≈184 запроса, параллельно по 3).
- **Частота опроса Казпочты:** **один раз в сутки, в 08:00 по Алматы** (`POLL_CRON=0 8 * * *`, часовой пояс `TZ_REPORTS`; решение клиента 2026-11-04). В запуск проверяются все посылки не в терминальном статусе, после него уходит одна сводка в Telegram.
  Статус в CRM и уведомление в Telegram приходят в течение пары минут после запуска (push-crm каждые 2 мин, dispatch каждую минуту). Новая сделка с треком попадает в базу при очередной синхронизации (каждые 10 минут) и впервые проверяется в ближайший слот 08:00. `/health` считает опрос зависшим через 26 часов (`HEALTH_POLL_STALE_HOURS`).
- Если в сделке несколько комментариев с разными треками, берётся новейший; смена трека сбрасывает историю отправления (`resetForNewTrack`).

### Проверено на живом аккаунте (2026-11-04, cloud.ncrm.pro)

- Токен работает; воронка «Воронка продаж» (id 2728): «НА ДОСТАВКЕ» = 18427, «УСПЕШНО ДОСТАВЛЕН» = 14276, «КЛИЕНТ НЕ ЗАБРАЛ ОТКАЗ» = 18747. Поле «Доставка» = 20156 (значения «Почта» / «Курьер»).
- `GET /api/deals/` — страницы DRF `{count, next, previous, page_size: 50, results}`; всего ~54 тыс. сделок, поэтому **обязателен серверный фильтр `?stage=<id>`** (для «НА ДОСТАВКЕ» ~180 сделок, 4 страницы). Фильтры `stage_id`, `stage_id__in` и `funnel_stage` молча игнорируются и отдают все сделки.
- В списке `stage_id` — **объект** `{id, stage_name, stage_color, finish_status}`, а в `GET /api/deals/{id}/` — число. `responsible` в списке — имя менеджера (строка), в карточке — id. `contact` — объект; `field_values[]` — `{id, value, field: <id поля>}`, для списка выбора `value` — текст («Почта»).
- Комментарии: `GET /api/notes/deals/{id}/` существует, ответ DRF-страницами `{count, next, previous, results}`; в `results` и комментарии, и системные события (`note_type`), дата — `created_date`, текст — `text`. Трек-код менеджера лежит в `text`.
- Время в API приходит без часового пояса и в UTC (06:56 в API = 11:56 в интерфейсе, UTC+5).
- `PATCH /api/deals/change_stage/` с `{"stage_id": N, "ids": [id]}` проверен: сделка переходит в нужный этап (4 сделки перенесены из «НА ДОСТАВКЕ» в «УСПЕШНО ДОСТАВЛЕН»). Ещё не проверено: `POST /api/notes/deals/{id}/` (запись комментария, `CRM_ADD_COMMENT=false`).

### Что реализовано и какие допущения заложены

Настройка: `CRM_DRIVER=ncrm`, `NCRM_BASE_URL`, `NCRM_API_KEY`, `NCRM_TRACK_FIELD_ID`, `NCRM_DELIVERY_FIELD_ID` (необязательно), `NCRM_KAZPOST_DELIVERY_VALUE`, `CRM_STATUS_MAP` (значение — id этапа).
ID полей и этапов выводит `pnpm ncrm:inspect` (нужны NCRM_BASE_URL и NCRM_API_KEY в окружении).

- **Список:** `GET /api/deals/`. Фильтра по дате нет, поэтому берутся все сделки и фильтруются по `changed >= cursor` на нашей стороне; каждые 10 минут — полная выгрузка.
  Если ответ — объект `{results, next}` (DRF), страницы читаются по `next` (только на тот же хост, токен добавляется заново; защита от зацикливания).
- **Допущения, которых нет в документации:** `field_values` в ответе — список объектов с ключом `field` (или `field_id`, `custom_field`, в т.ч. вложенный `{id}`) и `value` (строка/число/список/объект с `name|value|text`);
  `changed` — ISO-дата без пояса (разбирается как есть, одинаково для курсора и сравнения); `contact` — объект или массив с `full_name`.
  Любое несовпадение даёт `ExternalSchemaError` → `DEV_ALERT` (в алерт попадают только ключи объекта, без данных клиентов).
- **Смена этапа:** `PATCH /api/deals/change_stage/` `{"stage_id": N, "ids": [deal id]}`, ожидается 200/201/202/204; ретраи как у остальных запросов (операция идемпотентна).
- **Комментарий:** `POST /api/notes/deals/{id}/`, multipart, поле `text` = `{"message": "…"}`, без ретраев. В документации описан только для клиентов (`contacts`) — для сделок это предположение; включается `CRM_ADD_COMMENT=true`, сбой комментария не блокирует смену статуса.
- **Безопасность:** токен передаётся в URL, поэтому сообщения об ошибках HTTP-клиента никогда не содержат URL.

### Что проверить на реальном аккаунте в первую очередь
0. `pnpm ncrm:inspect <id сделки>` (например, 7350332): ключи сделки и комментариев; существует ли `GET /api/notes/deals/{id}/` и где в нём текст и дата.
1. Что токен пользователя видит нужные сделки (домен — `cloud.ncrm.pro`).
2. Реальный вид `GET /api/deals/` (массив или страницы, ключи `field_values`) и `changed`.
3. Что `change_stage` меняет этап и принимает такое тело; ID этапа «Получен».
4. Работает ли комментарий к сделке.
5. Объём выгрузки: если сделок тысячи, полная выгрузка раз в 10 минут может быть тяжёлой — спросить поддержку про фильтр.
